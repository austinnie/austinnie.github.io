## 痛点：一个具体的麻烦

上周组里推安全扫描自动化，我接到的需求很简单：在本地仓库和 CI 管道里都能跑 `cs scan .`，扫描完立刻能看到报告，能顺手把发现的问题处理掉。听起来不复杂吧？

结果一上手才发现，光是「跑通一次」就要经历好几个断层步骤：先去适配 Node.js 22.13.0+ / 24.x / 26.x 和 Python 3.10+ 的环境，装好 CLI，登录，跑扫描，然后从终端输出里扒拉 REPORT 路径，打开那个 Markdown 报告文件逐条看，再执行后续命令去查最新扫描结果、处理问题。每一个环节都是手动操作，环节之间的切换还要靠记忆或者笔记。

我算了一下，光是从打开终端到看完第一份报告，大概要 15～20 分钟的纯手工操作时间，还不算环境问题排查和反复重试。对于一个要在多个仓库、多条流水线里推广扫描的团队来说，这个成本完全不可接受。

## 之前我们是怎么做的

之前的流程大概是这样的，每一步都得人工介入：

**第一步：** 在每台机器上先把 Node.js 环境和 Python 环境配好，版本要对照文档一个个试。这一步最容易踩坑，不同机器的残留环境经常打架。

**第二步：** 用 `npm install --global @openai/codex-security` 把 CLI 装上，然后单独跑一遍 `cs login` 完成认证。如果是在 CI 里跑，还得提前把 API Key 塞进环境变量。

**第三步：** 切到目标仓库目录，执行 `cs scan .` 开始扫描，然后盯着终端等结果出来。

**第四步：** 等扫描跑完后，从终端输出的 REPORT 路径里找那个 Markdown 报告文件，开编辑器一个个看问题列表。这步完全没有自动化可言，纯粹是靠人眼读。

**第五步：** 看完报告之后，为了跟进进度或者查最新状态，再手动跑一遍 `cs scans show` 去拉取最新的扫描信息。

五步走完，人的精力消耗远比真正用于分析和修复漏洞的时间多得多。尤其是当仓库多了、流水线频繁触发的时候，重复劳动会让人崩溃。

## 为什么最后选了这个项目

其实我们一开始也评估过其他两个方案。一个是 SonarQube，另一个是 GitHub CodeQL。

SonarQube 在代码质量问题上做得很成熟，社区插件也多，但它是偏质量平台的路线，安全维度的深度扫描和支持程度都不够，尤其是对 AI 辅助分析、补丁生成这些能力基本没有。用它的话，安全扫描这块还得再接其他工具，链路会更长。

CodeQL 是 GitHub 生态里的老牌选手，免费好用，语法覆盖广，缺点是它更像是一个查询引擎，擅长发现模式但不擅长帮你验证发现、生成补丁或者直接对接项目管理系统。发现问题之后还是得手动流转，和我们想要的「扫描→验证→修复→跟踪」闭环还差一段距离。

选 codex-security 的核心理由是，它把扫描、验证候选发现、生成补丁、追踪到 Jira/Linear/GitHub、导出 SARIF/JSON/CSV 这几件事做成了一个相对连贯的工具链，而且本身就是 CLI + SDK 的形式，嵌进我们现有的 Node.js 工作流里没有额外负担。权衡下来，这是当时最贴合我们需求的选项。

## 关键步骤

实际跑通之后的流程被我压缩成了五步，每一步都有自己的作用：

**第一步：全局安装 CLI 并完成登录。**
```bash
npm install --global @openai/codex-security
cs login
```
安装是为了拿到 `cs` 命令，登录是为了让后面的扫描能调用后端能力。如果是 CI 环境，就把 `OPENAI_API_KEY` 或 `CODEX_API_KEY` 注入到环境变量里，避免交互式登录。

**第二步：在项目根目录跑扫描。**
```bash
cs scan .
```
默认会扫描整个仓库。如果只想扫特定目录，可以用 `--path` 参数限定范围，比如 `cs scan . --path src --path tests`。这一步是整个流程的核心触发点。

**第三步：从终端输出拿 REPORT 路径，直接打开报告文件。**
扫描跑完后，终端会把报告路径打印出来，按照 README 的描述，那是个 Markdown 文件，里面列出了发现列表、来源证据和排除项。不需要再去手动翻日志。

**第四步：用 `cs scans show` 查看最新扫描结果。**
如果想持续跟进某个扫描的状态，或者确认有没有新的发现，可以从同一路径下跑这条命令。它会列出最近的已完成扫描，方便快速定位最新结果。

**第五步：按需导出或对接外部分发系统。**
README 里提到支持导出 SARIF、JSON、CSV，也支持把发现同步到 Linear、Jira 或 GitHub。这样扫描结果就能直接进入我们原有的工单流转体系，不用再人工复制粘贴。

## 跑完之后

按 README 的描述，跑通之后的效果主要是这几个方面：

- 扫描可以在本地仓库、指定路径甚至 Git 变更范围内触发，Standard 模式和 Deep 模式可以选择，Deep 模式会重复执行 Standard 扫描并对发现去重。
- 报告以 Markdown 形式保存，包含发现详情、源证据和排除说明，终端会直接提示报告位置，不用手动检索。
- 可以通过 `cs scans show` 随时回查历史扫描记录和最新发现。
- 支持导出 SARIF、JSON、CSV，也可以将发现同步到 Linear、Jira 或 GitHub，方便并入现有的问题跟踪流程。
- 内置补丁生成和既有修复验证能力，配合 TypeScript SDK 可以在自动化流程里复用。

至于具体的性能数据、覆盖率、扫描耗时、与第三方扫描器的对接深度等内容，README 里没有给出明确的实测数字，我这边也没有完整跑过一遍所有功能，就不在这里编了。实际项目里能发挥到什么程度，建议大家对照文档在自己的仓库里试一下。

## 适合谁 / 不适合谁

适合的情况大概有三类：一是团队已经在用 Codex Security CLI/SDK，想把它嵌进本地开发或 CI 流程里；二是需要一个能从扫描一路走到验证、补丁生成和问题跟踪的轻量化工具；三是仓库规模属于中小型，不需要过于庞大的平台级架构。

不太适合的情况也有几种：一是团队已经有一套成熟的商业化安全扫描体系，且只想补充前端扫描能力的，可能引入新工具会带来维护负担；二是对 Node.js 和 Python 环境兼容性要求很严格、无法接受版本限制的；三是不需要手动干预、追求全量自动化的超大规模工程，这类场景可能更需要的是平台级的集成方案而不是 CLI。

一句话总结：如果你正在被手工扫描流程折磨，又想找一个能把扫描、报告、跟进串起来的东西，codex-security 值得一试。如果你已经有了更好的内部方案，那没必要为了换而换。
