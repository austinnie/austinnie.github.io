## 痛点：一个具体的麻烦

我们团队规模到 15 个人左右的时候，事情开始不对劲了。

工程组用 Slack + Linear，销售组用 HubSpot + Superhuman，产品和运营用 Notion + Slack。各管各的，谁也不嫌多。

真出事儿是这样的：周一早上打开邮箱，发现上周三有个客户邮件没回——因为发到了 @sales 群组，而那个群只在 HubSpot 里有备注，Slack 里没人提醒。中午开会，PM 说 Linear 里有个 bug 跟踪的是另一个 issue，因为有人在 Notion 里顺手建了个新页面没去改 Linear。下午产品想看上个月的转化率趋势，得先翻 HubSpot 导出 CSV，再打开 Notion 找对应的 PRD，最后回去看 Slack 里的讨论记录。

整个流程下来，一个原本 30 秒能回答的问题，平均要耗 3-5 分钟，而且还不一定找得全。Zapier 连的那些 automations 经常静默失败——一条 Zap 断了，没有任何地方会报警，直到你发现那个客户已经两周没人跟进。

MCP 那边也是，每个新入职的人都要花半小时配置自己的连接，而且不同的人配出来的东西还不一样。

## 之前我们是怎么做的

各团队用自己顺手的工具，没有统一标准。

具体做法是：Slack 里 @ 一下任务 Owner，去 Linear 手动复制粘贴创建任务，再把 Linear 链接贴回 Slack 原消息下面——三步，每步在不同应用之间切一次。要更新一个需求文档，先在 Notion 写正文，再去 Linear 更新任务描述，最后去 HubSpot 把相关线索标个记——又是四步。

Zapier 做了一些串联，比如"Linear 新建任务 → 发 Slack 通知"、"HubSpot 新建联系人 → 创建 Notion page"。但这些 flow 完全是手写的，没有版本管理，改起来靠猜。

最要命的是，这些数据彼此之间是孤立的。你在 Linear 里搜不到某封邮件的上下文，在 Notion 里也搜不到 Slack 里的讨论。跨系统的搜索？不存在。

## 为什么最后选了这个项目

其实我们没真正跑起来——原因下面会说。但对比了两个替代方案之后，Macro 是看起来最对的那一个。

**方案 A：把所有工具都迁到 One 个平台。** 比如全迁到 Notion，或者全迁到 Slack + 各种插件。问题是团队已经形成了牢固的工具习惯，迁移成本极高，而且任何单一平台都不可能同时满足工程、销售、产品三种工作流的需求。

**方案 B：继续用 MCP + Zapier 加强连接。** 这条路我们已经在走，而且越修越歪。Zapier 的 automations 已经积累了十几个，每个都需要单独维护，断链是常态。MCP 的连接也越来越多，但每个人配置出来的东西不完全一致，协作起来很痛苦。

Macro 的思路完全不同——它不是在你现有的工具之间建桥，而是从底层重新设计了一整套工作系统，把邮件、消息、文档、任务、CRM、AI Agent 全放进一个 interface 里，通过双向图把所有数据关联起来。对于 15-20 人的小团队来说，这个方向是对的。

选它还有一个原因：README 里明确说了，创始人就是把自己上一家公司做到约 20 人时遇到了同样的问题——"every team got their own tools and the company was held together by MCP and Zapier. The company was not computable." 这句话戳中了我们。

## 关键步骤

按 README 描述，部署 Macro 本身很简单，几步命令搞定：

**第一步：克隆仓库并构建**
```bash
git clone https://github.com/macro-inc/macro.git
cd macro
# 用 Make 构建
make build
```
为什么要这一步？因为 Macro 是本地部署的项目，Rust 编写，需要自己编译出来。这是所有后续配置的基础。

**第二步：初始化配置**
根据 README，Macro 会生成一个初始配置文件，你可以在里面设置自己的数据库（Postgres）和一些基础参数。这一步决定了你的数据存在哪儿、哪些功能模块开启。

**第三步：启动服务**
```bash
make run
```
启动后会在本地跑一个 web app，默认地址大概是 `http://localhost:3000`。

**第四步：配置各模块**
在 web interface 里依次设置：
- Email：接入你的 Gmail 账号
- Channels / Messages：创建团队频道
- Docs：开始写文档
- Tasks：创建任务
- CRM：录入客户
- Agents：配置你的团队级 AI memory

每一步都是独立的 block，但可以互相 @ 链接。

> 注意：以上是 README 里呈现的流程，实际使用中各模块的配置深度和集成复杂度没有详细说明，尤其是与外部系统（如 GitHub、现有邮件服务）的对接细节，文档里没有展开。

## 跑完之后

按项目文档描述，跑通之后你会得到一个界面，邮件收件箱、频道消息、文档、任务、CRM 记录全部在一个页面里切换，没有标签页跳转。

所有数据之间通过 @ 链接互相关联——你在文档里 @ 了一个任务，任务卡片上能看到是哪篇文档提的它，反之亦然。这种双向图关系是存在后端的，不是前端拼出来的。

Agents 共享团队级 memory，意味着你的 AI 助手知道团队里所有人的上下文，可以在邮件、文档、任务之间主动关联信息。

Calls 功能会把录音自动转写并记入团队 memory，方便后续检索。

File storage 会自动从邮件和频道里导入文件，并且可以被全文搜索。

Pull requests 可以从 GitHub 导入，与任务和频道消息关联。

这些是 README 里明确描述的能力。我们没有实测，所以不知道日常使用中的流畅程度、与现有工作流的兼容成本、以及长期运行的稳定性如何。文档里也没有提供任何性能基准或迁移指南。

## 适合谁 / 不适合谁

**适合：**
- 15-20 人规模、正在经历工具碎片化阵痛的新创团队
- 创始人/CTO 本人有技术背景，愿意自己部署和维护
- 团队工具习惯还不算太根深蒂固，接受"推倒重来"
- 想用 AI agent 作为团队协作者，而不仅仅是个人效率工具

**不适合：**
- 已经深度依赖某几个特定工具（比如离不开 Slack 的 threaded reply，或者离不开 Linear 的 sprint 视图）的团队
- 需要与企业现有系统（如现有的 ERP、复杂的审批流）紧密集成的场景——目前没有这方面的文档
- 不想自己运维基础设施的团队（这是 self-hosted 项目，不是 SaaS）
- 期待开箱即用、零配置的团队

实话实说，这篇文章的本质是一个"如果我去做，我会这么做"的思考框架，而不是一个实战报告。Macro 的方向是对的，但我们团队还没真正跑起来——主要卡在迁移成本和功能成熟度的评估上。如果你也在类似处境里，建议你先把它的 demo 跑一遍，感受一下界面和交互，再决定值不值得换。
