## 痛点：一个具体的麻烦

上周三凌晨两点，CI 流水线炸了。Slack 推送了一条红消息，我迷迷糊糊爬起来看——编译报错，但我完全不知道原因在哪，也没人告诉我怎么修。只能自己打开 Jenkins 控制台，一页页翻日志，找那个红色的 stack trace，然后去 Stack Overflow 搜类似问题，最后花了一个小时定位是某个依赖版本被上游更新了导致 break。第二天 standup 又被 PM 问为什么这次发布延迟了。

这种场景我们团队至少每周都能碰上两三次。每次都是同样的流程：收到通知→翻日志→猜问题→搜方案→试错→修好。有时候运气好能快速定位，有时候折腾半天发现只是个配置写错了。最烦的是，同一个问题隔几周又会出现一次，因为没人沉淀排查经验。


![illustration](/images/illustration_03.png)

## 之前我们是怎么做的

我们的排查流程很土，但也很真实：

1. **收到 CI 失败通知**：Jenkins / GitLab CI / GitHub Actions 推一条消息到 Slack 频道，附带构建链接。
2. **手动查看构建日志**：点进流水线页面，往上滚，找一个看起来像错误的行。
3. **尝试定位失败原因**：复制那段 error message，在脑子里（或者 Google）匹配有没有见过的 pattern。
4. **搜索解决方案**：去 GitHub Issues 或 Stack Overflow 搜关键词，看看别人踩过什么坑。
5. **手动实施修复**：改代码、改配置、重跑流水线，然后验证。

整个过程没有任何工具介入分析，全靠人的经验积累。一个新来的同学接手的成本很高，而且老同学休假的时候，团队整体 debug 效率会掉一半。

## 为什么最后选了这个项目

之前也看过几个方向，最终选了 OpenSRE。

第一个替代方案是用现成的 SRE 平台，比如 Datadog 或者 PagerDuty 的自动化剧本功能。但这些方案要么要付订阅费，要么配置复杂到要专门招一个人来维护规则。对于我们这种小团队来说，性价比不高。

第二个方案是自己写脚本解析日志。技术上可行，但要覆盖各种可能的失败类型几乎不可能——每个项目、每种错误格式都得单独处理，维护成本比想象中高得多。而且一旦 CI 平台升级或者报错格式变了，脚本又要改。

OpenSRE 吸引我的地方在于它是一个 CLI agent，部署简单，用的是本地模型而不是第三方 API，这意味着配置敏感信息不用往外传。README 里说它是 "self-hosted，with your own models"，这对我们这种对数据安全有要求的团队很重要。另外它的定位非常聚焦：就干一件事，读失败的构建记录，追踪根因，然后推送修复建议让你 review。不做多余的活，也不承诺做不到的事。

## 关键步骤

安装部分 README 写得很清楚，一步搞定：

```bash
curl -fsSL https://install.opensre.com | bash -s -- -gh
```

然后是启动 agent：

```bash
opensre
```

这里有个取舍——你需要提供一个 git 仓库路径，这样 agent 才能关联上下文。README 建议在运行 opensre 的项目目录下执行，它会利用 `.git` 目录里的 commit 信息和变更记录来做根因追踪。

接下来是关键的动作：让 agent 分析一次失败的流水线运行。从 README 的描述来看，它通过读取 CI 系统的失败记录（failed run），然后追溯相关变更来判断原因。实际操作中应该是类似这样的交互：

```
> 指定失败流水线的 ID 或引用链接
> Agent 开始分析（会展示进度和推理过程）
> 输出根因分析和可选的修复方案
```

README 提到修复建议会以 diff 的形式推出来，需要人工 review 后才应用。这点设计我觉得合理——AI 给出的修复可能有误，留给人来把关更安全。

## 跑完之后

根据 README 的描述，部署完成后，当 CI 流水线失败时，你可以调用 OpenSRE CLI agent 来分析失败原因并获取修复建议。它会读取失败的构建记录、追踪相关变更、给出根因推断，并以 diff 的形式推送修复方案供你审查。整个流程的核心价值是把「人从翻日志、搜文档、猜原因」这个过程里解放出来，让 agent 先替你完成信息收集和分析。

项目当前处于 public alpha 阶段，API 和集成方式可能会变化。这意味着如果你决定在生产环境用起来，要做好适配更新的准备。另外，它需要你自己提供 LLM 模型，无论是本地的 Ollama 还是其他兼容接口，这部分的基础设施需要提前准备好。

## 适合谁 / 不适合谁

**适合**：你的团队已经在用 GitHub Actions / GitLab CI / Jenkins 这类主流 CI 平台，希望减少重复性的人工排查工作量；你对数据安全比较在意，不愿意把构建日志和代码放到第三方 SaaS 上；你们已经有本地或自托管的 LLM 基础设施（比如 Ollama）。

**不适合**：你的 CI 系统是非标准的、很难拿到失败记录的私有部署；你期望开箱即用、零配置的方案（OpenSRE 目前还是需要自己装模型、配环境的）；你对 alpha 阶段的稳定性无法接受任何波动。
