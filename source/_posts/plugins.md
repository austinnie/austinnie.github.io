## 痛点

上周组里接了一个中等规模的内网工具迁移，涉及三个历史模块的重构和十几个接口的变更。按常规流程，每个 PR 提交后都要由两名同学做 code review。我的痛点很具体：**每次都要手动打开 GitHub 的 Diff 视图，逐行对比改动，把疑问、建议、潜在风险点写在评论框里，然后发出去等人回复。**

光是"看 diff + 写评论"这一套，一个小 PR 大概 20-30 分钟，一个大 PR 能拉到两三个小时。更烦人的是，reviewer 往往也是第一次看到这个模块的逻辑，读起来磕磕绊绊，提的问题集中在"这里为什么这么写""那个变量是从哪来的"这种基础认知问题上，而不是深层设计问题。

也就是说，很多时间在帮别人补课，而不是真正在做 review。


![illustration](/images/illustration_03.png)

## 之前我们是怎么做的

我们的老办法可以拆成四步：

1. **拉取代码分支，本地跑一遍测试**，确认没有挂掉就 commit 推送。这一步基本没得挑，但耗时约 10-20 分钟。
2. **去 GitHub 点进 PR 页**，点开 Files changed，一个个文件翻过去，边看边敲备注。如果页面卡顿或者 diff 行数过多，浏览器会明显变慢。
3. **针对疑问点截图 / 引用行号写评论**，有些问题需要来回跳转才能理解上下文，还要切回 IDE 查代码，注意力频繁被打断。
4. **把评论整理进文档或直接 @ reviewer 拉群讨论**，等待对方回应，再迭代一版。

这个过程最大的问题是：**信息是串行的**。你看 A 文件的疑问还没想清楚，就已经跳到 B 文件去了；等你回来，又忘了刚才的想法。而且每个 reviewer 关注点不同，往往要做两轮甚至三轮才能收敛。

## 为什么最后选了这个项目

其实一开始我们也试过另外两条路：

**替代方案一：手动加自动化检查工具。** 比如引入 SonarQube 做静态分析，或者配置 ESLint/Prettier 规则。这类工具确实能抓一些低级错误，但它们解决不了语义层面的问题——逻辑是否合理、命名是否清晰、有没有更好的抽象方式，这些它们完全不碰。而且维护这套规则本身就需要专人盯着。

**替代方案二：直接用通用 AI 助手做代码审查。** 我们把 PR 链接丢给 ChatGPT 或 Claude，让它输出 review 意见。问题在于：AI 对项目的上下文完全陌生，它不知道某个函数是 legacy code、知道某个变量的业务含义是什么。输出的意见要么太泛（"建议优化性能"），要么直接误判（"这段代码有 bug"其实是故意这么写的）。

相比之下，`cursor/plugins` 里的 **pr-review-canvas** 插件恰好解决了这两个缺口：它能把 PR diff 渲染成一个可导航的审查画布，并按重要性分组；同时配合 **thermos** 这样的深度审计插件可以做并行子 agent 审查。**选型理由很简单：第一，它直接在 Cursor 编辑器内运行，不需要切换窗口；第二，它通过 AGENTS.md 和上下文加载机制继承了项目的领域知识；第三，它是开放的插件体系，我们可以随时叠加或替换组件。**

当然也有代价：初始配置需要花半小时了解 manifest 结构和插件间的协作关系，且目前只支持 TypeScript 生态的项目，Java / Go 项目暂时不太适合。

## 关键步骤

整个跑通流程其实不长，核心五步：

**第一步：安装基础依赖并初始化项目。** 在 Cursor 里通过命令面板加载官方插件市场，安装 `pr-review-canvas` 和 `thermos`。这一步是为了拿到 canvas 渲染能力和深度审查能力。

**第二步：让 AI agent 读取 PR context。** 在插件里导入目标 PR 的 diff URL，它会调用 GitHub API 拉取 Changes 数据，并按文件模块自动聚类。之所以要把 diff 结构化而不只是扔文本，是因为 canvas 需要节点之间的引用关系来做高亮和折叠。

**第三步：触发分层审查。** pr-review-canvas 负责"广度扫描"——快速过一遍所有改动点，标记高风险区域；thermos 随后对这些高风险区域进行"深度审计"，包括 security check、correctness rubric、parallel subagent 并行验证。两层分开的原因是：广度扫描快但浅，深度审计准但慢，合在一起才能兼顾效率和准确性。

**第四步：审查结果注入 AGENTS.md。** 每个插件的输出都会以 bullet-point 形式追加到项目根目录的 AGENTS.md 中。这样做的好处是上下文会累积——下一轮 review 时 agent 不会再问同样的"这个函数从哪来"问题。

**第五步：生成可直接粘贴的 review 文案。** 最终产物是一个结构化的汇总文档，按优先级排列问题清单，同时附带每个问题的具体行号和修复建议。reviewer 可以直接复制到 PR 评论框，也可以进一步调整语气。

## 跑完之后

说实话，效果不能说一上来就惊艳，但它确实在某些地方起了作用：

**首先，阅读速度变快了。** 按 README 描述，canvas 的分组和高亮机制能让 reviewer 用更少的时间找到关键改动点。我自己感知到的是：以前看到一个大文件就会本能地想跳过，现在因为重点会被标红，反而更愿意主动点进去看。

**其次，问题分类更清晰了。** 以前 review 意见往往是杂糅在一起的，现在按 severity 分成了几个层级，哪些必须改、哪些可以商量、哪些只是建议，一目了然。

**再次，AGENTS.md 的积累确实有用。** 第二次做同一个仓库的 review 时，agent 已经记得上次提到的那些模式性问题，不再反复问同样的事情。这点在长期维护一个大仓时特别明显。

不过也要诚实说几点局限性：

- README 里没有给出完整的数字对比（比如"从 2 小时降到 30 分钟"），所以不能编造实测数据。按文档描述，它可以显著减少机械性阅读时间，但无法保证最终 review 质量完全取决于输入的质量。
- 它对多模态 PR（比如包含大量 UI 变动的项目）的支持有限，因为 canvas 主要处理代码 diff。
- 插件之间虽然协同工作，但如果某个子 agent 卡住，整体流程会阻塞，目前还没有很好的降级策略。

## 适合谁 / 不适合谁

**适合：**
- 日常有较多 Code Review 需求的中大型项目团队
- 希望标准化 review 产出格式、降低沟通成本
- 项目有一定规模、AGENTS.md 值得持续积累的团队

**不适合：**
- 纯一次性的脚本或小工具，不值得建这套流程
- 非 TypeScript / JavaScript 生态的主要项目，插件覆盖率不足
- 对 review 时效性要求极高（比如线上 hotfix）、来不及等插件异步聚合的团队
- 团队成员不愿意维护 AGENTS.md 的团队——没有积累，插件的效果会大幅打折
